Tiny JavaScript Kernel

How the whole machine works

A visual guide to the CPU, RAM, disk, filesystem, processes, scheduler, system calls, memory-mapped I/O, keyboard, framebuffer, IPC, and the programs running on top. The goal is not to imitate Linux line-for-line. The goal is to expose the core ideas of a real kernel in the smallest understandable form.

1. The big picture

The project is a simulated computer and kernel written in JavaScript. Node.js is the host environment, but the programs inside the simulated machine do not call Node directly. They execute our own machine instructions, use our own memory, load from our own filesystem, and talk to the kernel through our own mechanisms.

The central object is the process. A program becomes a process when the kernel loads its bytes into RAM, allocates private memory, creates CPU state for it, assigns a PID, and places it in the process table. The scheduler then repeatedly gives that process CPU time.

How it works in the code

There are two execution worlds. Node.js runs the kernel implementation (kernel.js, cpu.js, memory.js, and the rest). User programs are byte arrays on disk; only the simulated CPU executes them through cpu.run(). Programs never import Node modules or call JavaScript functions.

Entry & boot

main.js calls kernel.run(). kernel.js starts I/O bridges, spawns programs, and arms the timer.

Execution

cpu.js fetch/decode/execute loop. scheduler.js calls it on a timer. process.js holds the process table.

Memory & storage

memory.js is physical RAM plus address translation. filesystem.js and disk.js load programs from the simulated disk.

Kernel services

syscall.js dispatches kernel requests. ipc.js manages mailboxes. timer.js drives scheduling.

Programs on disk

asm.js assembles instruction helpers into bytes. disk.js embeds those bytes into the disk image at module load.

Host I/O

screen.js and keyboard.js bridge the simulated framebuffer and keyboard register to the real terminal.

The kernel main loop is not one function. Two independent setInterval loops run in parallel: the timer fires every 75 ms and calls scheduler.run(), which runs up to 56 instructions per ready process; screen.js polls the framebuffer every 33.3 ms (30 FPS) and redraws the terminal when pixels change.

Spawn is the bridge from program to process. The filesystem returns machine-code bytes, RAM receives those bytes, private data is allocated, and a process control structure is created.

How it works in the code

kernel.run() in kernel.js runs this exact sequence:

screen.start()          // clear terminal, start 30 FPS framebuffer poll
keyboard.start()        // raw stdin for arrow keys and WASD

process.spawn('/sbin/init')      // PID 1
process.spawn('/bin/animate')    // PID 2
process.spawn('/games/snake')    // PID 3
process.spawn('/bin/receiver')   // PID 4
process.spawn('/bin/sender')     // PID 5

timer.start(scheduler.run)       // 75 ms ticks begin

Spawn order fixes PIDs — the sender hardcodes receiver PID 4 because receiver is always spawned fourth. All five processes exist before the first scheduler tick; boot spawning is synchronous. screen.start() clears the terminal with ANSI escape codes, renders once, then polls every 33.3 ms. keyboard.start() enables raw TTY mode and maps physical keys to small integer codes.

Run the kernel from the project root with node main.js.

3. CPU and instructions

Programs are not JavaScript functions. They are arrays of raw bytes representing instructions for our simulated CPU. Every instruction is exactly 4 bytes. The CPU fetches, decodes, executes, and advances the instruction pointer unless a branch changes it.

CPU state

Per process

R0, R1, R2, R3
instructionPointer
zeroFlag

Registers and instruction pointer live in the process, so switching processes naturally switches CPU context.

Format

Fixed 4-byte instruction

[ opcode, a, b, c ]

Some instructions treat bytes 2–3 as a 16-bit value; others treat them as register numbers.

InstructionMeaningUse

LOAD16 / STORE1616-bit fixed-address memory access.Positions, indexes, lengths.

LOAD16_AT / STORE16_ATIndirect 16-bit access.Snake body ring buffer.

The assembler is only syntax sugar. MOV(R0, 72) becomes four bytes. Labels are resolved before execution; the CPU only ever sees numeric addresses.

Illustration: instruction fetch vs data access

Code and data use different paths in memory — this is easy to miss when reading cpu.js.

INSTRUCTION FETCH (every opcode)
  programStart + instructionPointer
        ↓
  memory.read(physical address)     ← raw RAM, no translation

DATA ACCESS (LOAD / STORE / LOAD16 / …)
  process-visible address in instruction
        ↓
  memory.readProcess(process, address)
        ↓
  keyboard | framebuffer | private data slot

How it works in the code

cpu.run(process, instructionCount) in cpu.js is the heart of execution. Each iteration:

instructionAddress = process.programStart + process.instructionPointer
opcode   = memory.read(instructionAddress)      // physical RAM
operandA = memory.read(instructionAddress + 1)
// decode and execute...
process.instructionPointer += 4   // unless branch, syscall block, or HALT

Instruction fetch uses physical memory. Code bytes are read with memory.read(), not readProcess(). Program code and process data live in different address spaces — the instruction pointer is a byte offset into the loaded program, not a process-visible address.

Branches set instructionPointer to a byte offset within the program. The assembler in asm.js resolves labels to these offsets in a two-pass assemble(): pass 1 records label addresses, pass 2 emits bytes.

SYSCALL calls syscall.handle(process, number). If the handler returns { blocked: true } (empty RECEIVE), cpu.run returns immediately and the instruction pointer is not advanced — the same SYSCALL is retried on the next scheduler slice.

HALT returns true to the scheduler, which calls process.exit().

NOP has an opcode in instructions.js but no explicit case in cpu.js. Unmatched opcodes still fall through to IP += 4. That is how /bin/animate slows itself — 54 NOPs per animation step consume CPU time without changing state.

How it works in the code

Program loading (memory.loadProgram): first-fit from freeProgramBlocks. The allocator takes bytes from the front of a free block — block.start advances as programs are loaded. On exit, freeProgram zeroes the region, pushes it back into the free list, and merges adjacent blocks.

Data slots (allocateData / freeData): at startup, memory.js precomputes a list of slot start addresses that fit before the physical framebuffer. Up to 8 slots of 61,440 bytes each. Allocation is freeDataSlots.shift(); free is push() plus zeroing the slot. No growth beyond precomputed slots.

Address translation in readProcess / writeProcess:

0xF800           → keyboard.read()
0xF000–0xF7CF    → bytes[FRAMEBUFFER_START + offset]  // shared
address < dataSize → bytes[dataStart + address]        // private
out of range     → read returns 0, writes dropped

Isolation example: PID 3 (snake) and PID 4 (receiver) both use address 0 in their programs, but it maps to different physical dataStart bases. Each process sees the same virtual layout; the kernel translates to separate physical slots.

How it works in the code

The disk image is built when disk.js loads — there is no separate build step. Programs are defined with assemble(...) from asm.js, the JSON file table is written to bytes 0–1023, and program binaries are laid out contiguously starting at offset 1024.

At spawn time, filesystem.read(path) calls resolve(path), which walks the JSON file table by matching parentDirID and name for each path component, then disk.read(file.start, file.size) returns a slice of the disk byte array.

The filesystem is read-only — there is no filesystem.write. Programs cannot create or modify files at runtime.

Each file table entry has id, parentDirID, type, name, and for files also start and size pointing into the raw disk byte array.

How it works in the code

process.spawn(path) in process.js runs this chain:

filesystem.read(path)
  → memory.loadProgram(bytes)     // copy into physical program area
  → memory.allocateData()         // take one private slot
  → build PCB { pid, state, programStart, dataStart,
                instructionPointer: 0, registers: [0,0,0,0] }
  → processes.push(newProcess)
  → ipc.register(newProcess)      // empty mailbox

The process table is a plain JavaScript array process.processes. PIDs auto-increment from 1 via nextPID. States are only 'ready' and 'blocked' — IPC receive sets blocked.

process.exit(currentProcess) frees program and data memory (zeroing the data slot), unregisters the IPC mailbox, and removes the PCB with splice. There is no zombie state — the process is gone immediately.

Context switching is just selecting a different PCB. The CPU reads and updates registers and instruction pointer stored on whichever process the scheduler passes in.

Illustration: one scheduler tick

Every 75 ms, each ready process runs up to 56 instructions. Blocked processes are skipped.

tick ─┬─ PID 1: run 56 instr ─┬─ PID 2: run 56 instr ─┬─ PID 3: run 56 instr
      ├─ PID 4: skip (blocked on RECEIVE)
      └─ PID 5: run 56 instr ──► may SEND and wake PID 4 for next tick

How it works in the code

scheduler.run() in scheduler.js iterates a snapshot [...process.processes] on every timer tick. Each 'ready' process gets up to 56 instructions (TIME_SLICE) — not one process per tick. All ready processes run during each 75 ms tick.

Blocked processes are skipped entirely until ipc.send sets their state back to 'ready'. Within one tick, a process runs 56 instructions uninterrupted unless it blocks on a syscall or halts.

The timer in timer.js uses setInterval(onTick, 75) — about 13.3 kernel ticks per second. This is independent of screen.js, which refreshes at 30 FPS.

8. System calls

Normal CPU instructions handle local computation and memory access. A syscall is used when a program needs a kernel-owned service. Arguments and return values use registers.

No.NameInputResult
1RANDOMR0 = maxR0 = 0..max-1
2SENDR0 = PID, R1 = messageR0 = 1/0; wakes blocked receiver.
3RECEIVEnoneR0 = sender PID, R1 = message; blocks if empty.

Blocking RECEIVE: when no message exists, the process becomes blocked and the CPU returns without advancing the instruction pointer. When SEND later wakes it, the same RECEIVE instruction is retried.

How it works in the code

syscall.handle(process, number) in syscall.js reads and writes registers on the PCB. Programs never call JavaScript directly — the CPU routes SYSCALL instructions here.

  • RANDOM (1): treats R0 as max, replaces it with floor(Math.random() * R0).
  • SEND (2): ipc.send(senderPID, R0, R1); R0 becomes 1 on success, 0 if destination PID has no mailbox; wakes a blocked receiver.
  • RECEIVE (3): FIFO shift() from mailbox, or block if empty; on success R0 = senderPID, R1 = value (masked to 16 bits).
  • Unknown numbers: no-op, returns { blocked: false }.

This machine exposes devices through special addresses. Programs use ordinary memory instructions; memory.js decides whether an address means private RAM or device hardware.

3 = down

There is no keyboard or framebuffer syscall because this machine deliberately permits direct MMIO. That is a design choice, not a universal OS rule.

How it works in the code

Framebuffer writes: a STORE to 0xF000+ goes through writeProcess into bytes[FRAMEBUFFER_START + offset] — the same physical cells for every process. All programs share one screen.

Screen rendering: screen.js calls memory.readFramebuffer() every 33.3 ms, builds an 80×25 character grid with a box-drawing border, and writes \x1b[H to move the cursor home. It skips redraw when previousFrame matches — unchanged frames do not touch the terminal.

Keyboard reads: keyboard.read() returns the pending key code then resets to NONE. One LOAD consumes one keypress — holding a key does not auto-repeat into the register.

Host escape: Ctrl+C in raw mode restores normal TTY and calls process.exit(0) on the Node host.

Each process gets a kernel-managed mailbox. Processes stay isolated; SEND and RECEIVE are the explicit bridge between them.

→
PID 4 receiver
SYSCALL RECEIVE
R0=5, R1='!'
Queue

Messages are appended to a per-process FIFO mailbox.

Block

An empty RECEIVE marks the process blocked so it stops consuming CPU time.

Wake

SEND to a blocked process marks it ready again.

This is real kernel-mediated IPC in miniature. Sockets, pipes, channels, ports, and message queues are richer solutions to the same fundamental problem: isolated processes need an explicit way to communicate.

Illustration: mailbox before and after SEND

  messages: []
  process.state: 'blocked'

How it works in the code

ipc.js stores mailboxes in a Map: PID → { process, messages: [] }. Each message is { senderPID, value } with value & 0xffff.

Send: push to destination FIFO. If mailbox.process.state === 'blocked', set 'ready'. The receiver does not run until the next scheduler tick.

Receive: if mailbox empty, set process state = 'blocked' and return null (syscall blocks). Otherwise FIFO shift().

The demo sender in disk.js hardcodes RECEIVER_PID = 4 because spawn order in kernel.js is fixed — receiver is always the fourth spawn.

13. Deliberate simplifications

This is a real model of kernel ideas, not a production OS. The simplifications are what keep the mechanisms visible.

Scheduler
  • Round-robin pass over the process table.
  • Fixed 56-instruction slice.
  • No priorities, multicore, or sophisticated fairness.
  • Timer uses JavaScript setInterval, not a hardware interrupt controller.
Memory
  • No paging or MMU page tables.
  • Program code: variable first-fit blocks.
  • Private data: fixed 60 KiB slots.
  • Process-visible addresses are translated in software.
Filesystem
  • JSON metadata in first 1024 disk bytes.
  • Contiguous files; no block allocation or fragmentation.
  • No permissions, timestamps, links, cache, or journal.
  • Runtime file support is deliberately minimal.
Devices
  • Text framebuffer, one byte per character.
  • Keyboard keeps only the latest key code.
  • Programs may directly access MMIO.
  • No privilege rings, DMA, or device discovery.
IPC
  • One mailbox per process.
  • Message = sender PID + one 16-bit value.
  • No named ports, capacity limits, permissions, or backpressure.
  • Demo sender assumes receiver is PID 4.
Host boundary
  • Node executes the JavaScript kernel implementation.
  • The simulated CPU executes only our user-program machine code.
  • screen.js and keyboard.js bridge to real terminal I/O.
  • The 64 KiB kernel RAM region is conceptual rather than literal executable JS bytes.
These simplifications do not remove the core relationships. Programs live on disk, files have names and directories, programs become processes in RAM, the scheduler shares CPU time, syscalls enter kernel services, MMIO connects software to devices, blocked tasks stop running, and IPC lets isolated processes communicate.

Implementation details worth knowing

  • The first 64 KiB kernel RAM region is documented but unused — the JavaScript kernel does not occupy simulated RAM.
  • Maximum about 8 concurrent processes due to fixed data slot count; no dynamic slot growth.
  • Program instruction fetch bypasses address translation — only LOAD/STORE use readProcess / writeProcess.
  • Scheduling is cooperative within a tick: all ready processes each get 56 instructions per 75 ms tick, not strict one-at-a-time round-robin.
  • The disk image is static at startup — programs are embedded in disk.js when the module loads.

Every box in the diagram maps to a real module: keyboard.js feeds 0xF800, screen.js reads the physical framebuffer, filesystem.js resolves paths against the disk file table, process.js holds the process table, scheduler.js and timer.js drive execution, cpu.js runs instructions, memory.js owns the RAM array, syscall.js and ipc.js handle kernel services, and disk.js is both the simulated disk and the program authoring surface.

15. What this kernel teaches

Once a machine has a CPU, memory, storage, devices, and multiple programs, the core OS problems naturally appear. This project derives the major mechanisms directly from those problems instead of starting from textbook names.

Execution

Programs become processes with PID, registers, instruction pointer, and memory.

Sharing

The scheduler divides CPU execution among ready processes.

Isolation

Each process receives private data memory.

Services

Syscalls cross from programs into kernel-owned functionality.

Persistence

The filesystem gives raw disk bytes names and hierarchy.

I/O

MMIO connects programs to keyboard and framebuffer.

Waiting

Blocked processes stop consuming CPU until woken.

Communication

IPC lets isolated processes exchange messages through the kernel.

How to run and read the code

From the project root, run node main.js. Trace boot from main.js → kernel.run() → spawn chain → first scheduler.run() tick.

To follow one instruction: set a breakpoint or log in cpu.run at the fetch line — watch programStart + instructionPointer read from physical RAM. To follow one memory access: trace readProcess in memory.js and see whether the address routes to keyboard, framebuffer, or private data.
